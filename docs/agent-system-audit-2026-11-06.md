**B01 · P1：一条提醒发送失败，会连带丢失同批后续提醒**

同一用户的 A、B 两条提醒在一个 tick 中到期，A 发送失败。系统会给 A 安排重试，但 B 从未尝试发送，也没有失败或重试记录。一次性 B 会一直保持 `done=True`；循环 B 则漏掉本次触发。

根因在 [private_scheduler.py:180](../src/plugins/yawn_core/yawn_agent/private_scheduler.py#L180)：先调用 `collect_due()` 并持久化所有到期任务的推进结果，然后逐条执行；第 187 行遇到首条失败就 `break`。[private_schedule.py:377](../src/plugins/yawn_core/yawn_agent/private_schedule.py#L377) 已将一次性任务标为完成、循环任务推进到下次；第 359 行又会跳过没有重试计划的已完成任务。未执行的 B 因此没有机会进入 `finish()`。

隔离复现结果：第一次调用发送器只出现 A；3 分钟后网络恢复，调用序列为 A、A，B 仍留在个人数据中且 `done=True`，没有 `retry/history`。使用真实 `private_schedule` 模块和从当前源码编译的 `run_tick()`、`_run_firing()`，存储与发送器为内存替身。

最小修复：让每个已经领取的 firing 都经过执行和结果登记，删除当前批处理里“首条失败就退出”的控制流。沿用现有失败退避机制，无需新建调度系统。

验收：A 失败不能使 B 消失；B 要么本次成功，要么有可查询的失败结果和重试计划。

**B02 · P1：群回复尚未转发成功，就被永久标记为已送达**

用户让 Bot 在群内提问，群友引用该提问回答。转发回私聊时，只要 `send_private_msg()` 明确失败，这批回答便不再进入后续待发送集合。用户只能看到“没人回复”般的沉默。

[agent_bridge.py:518](../src/plugins/yawn_core/yawn_agent/agent_bridge.py#L518) 的 `take_undelivered()` 读取回复时立刻把 `delivered=True` 写回。真正发送发生在第 584 行。第 571 行的异常处理只记日志并移除调度任务，没有恢复待发送状态。

复现使用真实 relay、回复记录和个人数据存储，发送器抛出模拟失败。失败后回复仍为 `delivered=True`，再次取待发送回复得到空数组。正文尚在存储中；丢失的是自动投递机会，并非正文被物理删除。

最小修复：把读取待发送回复与确认送达分开；仅确认本次成功发送的具体回复，失败保持待发送并安排重试。确认时不能顺便标记发送过程中新增的回复。

验收：明确失败后仍能重试原回答；成功的回答不被重复发送；等待期间新增回答不被错误确认。

**B03 · P1：删除语义在不同读取链路中不一致**

这项包含两个入口，影响的是删除后的原文再次进入 Agent，不等同于“删除聊天自动清除所有既有派生记忆”。

第一种：在 QQ `/面板` 删除单条消息。[panel_router.py:282](../src/plugins/yawn_core/panel_router.py#L282) 设置 `ChatMessage.is_deleted=True` 并显示“已删除消息”，正常对话加载会排除该消息。但是 [private_agent.py:1528](../src/plugins/yawn_core/yawn_agent/private_agent.py#L1528) 的 `_recent_history()` 只按会话 ID 查询，没有检查消息删除标记。后台汇报、协调、等候恢复、定时回合、群转私聊和主动提议会使用这个函数。

第二种：在网页删除整段对话。[me_insight_routes.py:660](../src/plugins/yawn_core/webui/me_insight_routes.py#L660) 只设置 `ChatSession.is_deleted=True`。但 [private_memory.py:309](../src/plugins/yawn_core/yawn_agent/private_memory.py#L309) 的整理输入，以及 [private_services.py:196](../src/plugins/yawn_core/yawn_agent/private_services.py#L196) 的聊天检索，只排除已删除消息，没有排除已删除会话。会话里的未逐条删除消息仍可进入记忆整理和召回。消息计数也存在同样遗漏。

两项均以内存 SQLite 复现：单条软删除正文出现在 `_recent_history()` 结果中；整段软删除正文同时出现在 `_recent_user_lines()` 和 `_private_messages()` 结果中。未调用真实模型，验证的是实际传给后续模型组装路径的数据。

最小修复：所有私聊历史读取统一遵守消息删除与所属会话删除两个条件；保留现有两种软删除标记。对正在执行的回合，还需明确删除生效边界，不能将静态查询修复宣称为已撤回发送给外部模型的数据。

验收：删除内容不出现在正常对话、后台汇报、召回、记忆整理、计数和提示词预览的后续读取中。

**B04 · P2：删除等写操作成功后，Agent 仍可以不回复**

例如用户要求删笔记，工具已真正删除，但模型随后返回 `【不回】`，整轮没有任何确认。用户无法区分已执行、未理解和失败，容易重复操作。

[private_agent.py:1201](../src/plugins/yawn_core/yawn_agent/private_agent.py#L1201) 计算了较宽的写操作标记 `wrote`，但第 1218 行沉默分支和第 1232 行空回复兜底只检查另一份 `_WRITE_RESULTS`。该集合遗漏 `notes.delete` 等动作，导致执行结果与回复决策口径不同。

复现实际创建并删除临时笔记，只模拟模型输出。结果：笔记已不存在，`handle_private_turn()` 返回空字符串，Bot 发送列表为空。

最小修复：统一“本轮实际发生了修改”的判定，供沉默、让出回合和空回复处理使用。应以实际动作结果为准；不能简单把 `notes.list` 等同一工具族的只读调用也视为修改，更不应继续零散补多个工具名集合。

验收：真实修改成功后有与结果一致的最短确认；只读查询仍保留合理的沉默能力；不能用通用成功文案掩盖工具失败。

**B05 · P2：回复条数上限会静默丢弃用户需要的产物**

私聊发送图片、文件时，文本与每个媒体各算一个发送项。组合回复超过 6 项后，[private_delivery.py:213](../src/plugins/yawn_core/yawn_agent/private_delivery.py#L213) 只保留前 5 项，尾部仅合并文本，图片和文件直接被过滤。被删项不进入发送循环，也不会计入媒体失败提示。

复现输入为“第一张图 + 图片 A + 第二张图 + 图片 B + 第三张图 + 图片 C + Excel 文件”。真实规划函数仅返回前 5 项：两张图片及三段文字，第三张图片和最终文件全部消失。这个例子中甚至没有使用完整的 6 条额度。

最小修复：收敛文本分条时保留文件/图片产物；先合并说明文字。如果媒体本身超过硬上限，必须明确告知未发送的产物，不能静默丢弃。沿用当前发送器与发送结果记录即可。

验收：上述 7 项输入的三个图片和一个文件均被实际安排发送，或有明确的未发送清单；历史只记录实际送达内容。

**B06 · P2：编辑已取消群任务显示成功，却不会重新执行**

取消任务后，再要求“把刚才取消的任务改到明早”，调用 `update_scheduled_task(action=edit, kind=once, ...)` 可以成功修改时间和正文，但任务仍是 `cancelled`、`next_run_at=None`。

[tool_handlers/schedule.py:366](../src/plugins/yawn_core/yawn_agent/tool_handlers/schedule.py#L366) 放行已结束任务的编辑，并明确提示“已结束的任务可以用 action=edit 改时间重新启用”。但 [schedule_store.py:457](../src/plugins/yawn_core/yawn_agent/schedule_store.py#L457) 仅恢复 `completed/failed`，遗漏 `cancelled`。工具最终仍返回 `updated=True`。同文件第 478 行的领取逻辑只处理 `active` 且有下次运行时间的任务。

隔离执行真实 `apply_draft()` 后，任务正文已更新，状态仍为 `cancelled`、下次执行时间仍为空。

最小修复：按现有工具承诺，在用户明确提交新的完整调度规则时恢复已取消任务，设置下一次时间并清理取消元数据，沿用现有权限和额度检查。不能把“仅改标题”等无恢复意图的操作一概当作重新启用。

验收：取消后明确改到未来时间，结果与实际可调度状态一致；再次查询能看到明确的下次触发时间。

**B07 · P2：提示词保存发生版本冲突时，本地草稿被清空**

复现路径：在私聊提示词编辑器输入较长修改 → 另一处更新版本 → 保存收到 409。界面提示“已刷新，请确认后再保存”，但刚输入的草稿已经变回服务端文字。

[PromptsTab.tsx:228](../webui/src/private-agent/PromptsTab.tsx#L228) 遇到 409 会刷新目录；第 502 行把 `revision` 放进编辑器的 React `key`。版本改变导致编辑器重新挂载，本地编辑状态随之丢失。版本变化不一定来自当前分段，其他分段的更新也可能触发该机制。

组件复现实际观察到“本地尚未保存的详细草稿”被替换为“叫他小明”。

最小修复：编辑器身份只由分段、作用域和用户决定，不能绑定版本；基准版本、服务端新内容、本地草稿分别保留。冲突时展示差异，由用户选择重新载入或确认合并。

验收：收到 409 后草稿逐字保留，服务器修改也可查看；再次保存仍执行版本检查。

**B08 · P2：“保留我的草稿”不能真正解决群配置与人设冲突**

复现路径：加载 v1 并修改 → 服务端更新成 v2 → 点击“保留我的草稿” → 再保存。请求仍带 v1，后端再次返回 409；同一个 v2 的冲突提示还被抑制，比较和重新载入入口不再出现。

[shared.tsx:242](../webui/src/shared.tsx#L242) 的 `keepDraft()` 只记录 `ignoredVersion` 并隐藏提示。[AgentConfigPanel.tsx:75](../webui/src/agent-panels/AgentConfigPanel.tsx#L75) 和 [PersonaPanel.tsx:119](../webui/src/agent-panels/PersonaPanel.tsx#L119) 继续提交旧 `baseVersion`；[route_helpers.py:39](../src/plugins/yawn_core/webui/route_helpers.py#L39) 必然拒绝不相等的版本。该项通过完整代码链确认，未额外运行组件复现。

最小修复：让“保留草稿”保留可解决的冲突入口；用户明确比较并确认合并后，再把新版本作为提交基线。不能只是静默换版本后覆盖远端，也不能把隐藏警告当作解决冲突。

验收：用户不需要复制草稿、刷新页面、重新填写，也能在页面内解决冲突并保存。

**B09 · P2：刷新用户人设列表会覆盖未保存的策略**

将“本人每天最多改”从 10 改为 77，暂不保存，然后点击“刷新人设列表”：输入立即回到 10，保存按钮恢复禁用。

[PersonaTab.tsx:76](../webui/src/private-agent/PersonaTab.tsx#L76) 无条件执行 `setDraft(policy)`。列表接口同时返回策略，每次刷新产生新的对象，即使策略内容没变，也会覆盖草稿。第 304 行策略卡与第 309 行列表刷新共用同一请求结果。搜索、筛选等同样会触发这条数据更新链。

已通过组件复现上述 77 → 10 的变化。另从代码看到，私聊页切换子页使用 `destroyOnHidden`，策略编辑也没有注册离开保护；这属于同类草稿生命周期问题，未单独计数或另跑场景。

最小修复：复用项目已有草稿保护机制，只在未编辑或用户明确重新载入时同步服务端数据；离开有草稿的页面应保留或提示。

验收：刷新列表、搜索用户和切换筛选不会覆盖策略草稿；远端策略变化能提示并比较。

**B10 · P2：从消息进入调试后，点击 Trace 分析无效**

消息页点“调试”会附带 `debug.messageId`，自动打开模拟实验室。此时点击“Trace 分析”仍停留在实验室。从真实 Trace 发起回放也有同样路径。

[AgentDebugger.tsx:32](../webui/src/agent-debug/AgentDebugger.tsx#L32) 在没有显式 `debug.view` 时根据 `debug.messageId` 选择实验室；第 36 行切到 trace 却只删除 `debug.view`。旧消息 ID 还在，下一次渲染又选择实验室。

已通过路由和组件复现。

最小修复：用户明确切换 Trace 时写入 `debug.view=trace`，让明确选择优先于用于首次进入的默认推断，无需丢弃消息上下文。

验收：携带消息 ID 进入、回放后返回、浏览器刷新等路径，标签与 URL 表达的视图一致。

**B11 · P2：Trace 自动刷新只更新列表，不更新已选详情**

选中正在执行的 Trace，等待任务完成后，列表已经显示 completed，右侧详情仍显示 running、旧事件和旧诊断。管理员容易误判执行卡住；基于当前详情导出的内容也可能过时。

[useExecutionTraces.ts:205](../webui/src/agent-debug/useExecutionTraces.ts#L205) 的详情查询只跟随群号和选中 ID。第 215 行轮询刷新仅更新列表和统计，不更新详情。手工刷新有单独调用详情刷新，因此能恢复。

Hook 复现中摘要从 running 变成 completed，详情仍为 running，详情请求次数始终为 1。

最小修复：选中 Trace 的摘要状态或事件数变化时刷新该详情，避免无条件刷新全部历史详情。

验收：在不重新选择、不手工刷新的情况下，当前执行的最终状态、事件和导出内容自动一致。

**B12 · P2：提示词导入失败仍关闭弹窗、清空内容**

粘贴有效导入 JSON 后，请求遇到断网、后端校验失败或 409，页面虽然显示错误，却关闭导入框并清空输入。注意：JSON 本身无法解析时会提前返回，不受本项影响。

[PromptsTab.tsx:369](../webui/src/private-agent/PromptsTab.tsx#L369) 的 `runBulk()` 捕获异常但不向上返回失败；第 399 行的 `doImport()` 等它正常结束后，无条件关闭弹窗并清空文本。该项由调用链确认，未额外运行组件测试。

最小修复：让批量操作返回明确成功状态，只在成功时关闭和清空。失败保留输入、错误与重试入口。

验收：请求失败后原 JSON 逐字保留；修正条件后可直接重试。

**B13 · P2：群隐私列表只能管理最新 100 条记录**

当群内隐私记录超过 100 条时，较早记录的成员无法通过该页面找到和操作。表格仍表现为有分页，容易让管理员以为已经浏览全部记录。成员自己仍能使用 `/Agent隐私`，问题限定在后台页面。

[PrivacyPanel.tsx:10](../webui/src/agent-panels/PrivacyPanel.tsx#L10) 固定请求 `pageSize=100`，仅保留 `r.data`；第 25 行直接将这 100 条交给表格，没有服务端页码和 total。后端 [agent_privacy_routes.py:109](../src/plugins/yawn_core/webui/agent_privacy_routes.py#L109) 实际按页查询。因此前端表格只能翻已下载的 100 条，不能加载后面的记录。

该项由前后端分页代码确认，未创建 101 条真实记录。

最小修复：接入现有服务端分页及总数；按成员查找应使用同一查询接口，避免再建一套名单。

验收：构造 101 条记录，最早的一条可以被找到、查看并操作。

**另两处交互困惑**

**U01：提示词作用域存在两个“切换”入口，只有一个实际生效。** [PromptsTab.tsx:439](../webui/src/private-agent/PromptsTab.tsx#L439) 中，输入 QQ 后点击“某位用户”，只把输入框设为原值，不改变 `pa.user`，所以仍在全局作用域；必须点旁边“切换”才生效。页面的全局选中状态仍可见，因此不能说系统偷偷切换了作用域，但这个按钮本身的动作与名称不符。建议统一成一个明确的用户选择动作，并在保存处醒目标明影响所有私聊还是某个用户。证据为代码审查。

**U02：群回合排队过期或队列满时，调用者没有终态反馈。** [collector.py:195](../src/plugins/yawn_core/yawn_agent/collector.py#L195) 的过期分支直接跳过；[agent.py:390](../src/plugins/yawn_core/yawn_agent/agent.py#L390) 在入队失败时仅记录日志。120 秒排队 TTL 与有界队列本身合理，但在前一个沙箱回合很慢时，后续明确 @ 的用户无法知道自己的请求已被丢弃。建议对明确触发合并、限频发送一次“排队超时，请重发”类终态反馈，并保留诊断原因；不要对普通群消息逐条刷提示。未运行真实负载测试，本项结论只覆盖上述两个确定退出分支。

**修复顺序与收敛方向**

第一批处理 B01、B02、B03：先恢复提醒、协作投递和删除边界的正确性。它们会造成用户未收到结果，或让已删内容重新进入处理流程。

第二批处理 B04、B05、B06：保证工具实际发生的动作与最终反馈一致，成功必须能解释，失败或未交付必须能看见。

最后处理 B10、B11、B13、U01、U02：修复导航、状态刷新、列表完整性和终态反馈。前三者代码改动预计较集中，可与前两批并行，但优先级不应挤掉数据正确性修复。

这次问题集中在三类边界：副作用完成与状态确认顺序不一致；同一数据的不同读取路径遵守不同规则；服务端刷新与本地编辑状态相互覆盖。最佳方向是在现有模块内统一这些边界，避免增加新的状态库、调度器或第二套编辑流程。
